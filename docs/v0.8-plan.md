# ScriptCraft v0.8 — revision-complete plan

Status: M0 complete 2026-10-26. Depends on the v0.7.0 release.
Target: 8–10 weeks of focused work.

## Why this release

v0.7 made revisions visible and printable. v0.8 makes them usable for a full
production cycle: compare two drafts, restore an earlier one safely, omit
scenes, handle dual dialogue, edit the title page, and issue a revision
summary. It is the release that lets a working writer replace a paid app for a
revision-heavy show without explaining away a missing workflow.

The revision workflow is also the forcing function for the foundations the rest
of the roadmap needs: stable scene/block identity, a versioned sidecar schema,
deterministic layout, and FDX fidelity.

## Definition of done

A writer can:

1. Open a KIT or FDX project and start a Blue revision.
2. Edit, lock pages and scene numbers, and export a page-exact Blue PDF/FDX.
3. Start Pink, edit again, and compare Blue vs Pink against the current draft.
4. Jump between added, removed and changed blocks; see which scenes and pages
   changed; export a revision summary.
5. Restore Blue as a **copy**, leaving the current draft untouched.
6. Omit a scene without losing its number, and add dual dialogue that prints
   correctly.
7. Edit the title page and see the exact exported result.
8. Save, reopen, and find every block and scene identity intact.
9. Do all of the above offline, with no account, on a signed/notarised build.

Non-goals for v0.8: collaboration/CRDT, comments, plugin API, AI, production
breakdowns/tagging, DOCX/RTF, spellcheck, mobile, a new native project format,
and a full accessibility overhaul. Those are later releases.

## Current state

Already shipped in v0.7:

- `RevisionColor`, `RevisionSet`, `RevisionHistory`, block baselines and
  deterministic mark computation (`scriptcraft-core/src/revision.rs`).
- Coloured margin bars, revision-pages mode, revision history window, page-count
  baselines, KIT saved-version import.
- Revision colours/`*` marks and revised title-page fields in FDX; revision
  pages, margin bars, header/footer tokens and Revised fields in PDF.
- Locked pages/scenes with content anchors, `42A`/`42B` numbering, separate
  scene-number locking (`scriptcraft-core/src/page_lock.rs`).
- 500-page revision diff under 8 ms in the scale test.

Already shipped in v0.8 development:

- **M0 identity and sidecar schema (2026-10-26).** `ScriptBlock.id` and scene
  identity survive save/reopen, scene reorder, inserted/deleted blocks and
  in-place external edits. Versioned `scenario_data.scriptcraft_ids` and
  `scriptcraft_scene_meta` rows; re-anchoring by KIT UUID, exact type + text,
  then equal-shape runs; ambiguous edits warn instead of guessing. A95
  round-trip tests cover the new rows.

Known gaps this plan closes:

- no draft comparison or restore;
- no omitted-scene state;
- no dual dialogue in the model or layout engine;
- no dedicated title-page editor;
- no revision summary;
- Windows/Linux packages are compiled but not runtime-tested;
- macOS builds are not notarised; Dock/AppleScript quit bypasses the save
  prompt;
- `ROW_MM` is still a hardcoded metric;
- `scriptcraft-app/src/app.rs` is a 7,000-line monolith.

## Milestones

### M0 — Identity and sidecar schema (foundation)

Goal: stable block and scene identity that survives save/reopen, reordering and
an external KIT edit.

Tasks:

- [x] Write the schema decision in `docs/kitsp-format.md`: a versioned
      `scenario_data.scriptcraft_ids` row and a `scriptcraft_scene_meta` row.
      KIT ignores unknown rows; the normal atomic save path must preserve them.
- [x] Persist `ScriptBlock.id` aligned with `scenario` order. On load:
      re-anchor by `kit_uuid`, then exact element type + text, then equal-length
      same-element runs between anchors; assign new IDs only to genuinely new
      blocks. Never silently reuse an ID for different content.
- [x] Give every scene a stable `SceneId`, derived from its heading block ID.
      Store per-scene metadata (at minimum `omitted`) keyed by `SceneId`.
- [x] Add a `schema` version to both rows and a migration path for projects
      without them. Old projects must open unchanged.
- [x] Document the external-edit policy: if KIT rewrites the script and
      re-anchoring is ambiguous, preserve the script and warn; never drop the
      sidecar.
- [x] Add tests for save/reopen, reorder, duplicate headings, external edit,
      missing rows, and an A95 round-trip that preserves every existing KIT
      table/row and adds only the new sidecar rows.

Acceptance:

- [x] IDs are stable across save/reopen and scene reordering.
- [x] A95 plus the new rows round-trips; existing KIT tables are untouched.
- [x] A project with no sidecar opens, gets IDs, and saves cleanly.
- [x] An ambiguous external edit produces a visible warning (`LoadReport`), not
      silent data loss.

Estimate: 1.5 weeks.

Implementation notes (2026-10-26):

- `scriptcraft-core/src/kitsp.rs`: `LoadReport`, `scriptcraft_ids`,
  `scriptcraft_scene_meta`, schema guards, re-anchoring, atomic-save writes.
- `scriptcraft-core/src/model.rs`: stable `Scene.id`, `SceneMeta`,
  `Project::scene_meta`, `retain_scene_meta`, `set_scene_omitted`.
- `scriptcraft-app/src/app.rs`: open path surfaces load warnings in the status
  bar.
- `scriptcraft-core/tests/test_identity.rs`: 12 tests covering reopen, missing
  rows, reorder, duplicate headings, insert/delete, text edits, replacements,
  scene metadata, invalid rows and newer schemas. `test_a95.rs` now asserts the
  new rows without weakening the untouched-table check.

### M1 — Draft diff engine

Goal: a public, deterministic comparison between any two revision baselines, or
a baseline and the current script.

Tasks:

- [x] Refactor the internal `diff_range`/`split_segments` work in
      `revision.rs` into a public `DraftDiff` API. Block-level, not
      character-level.
- [x] Add `block_id: Option<Uuid>` to `RevisionBlock` with
      `#[serde(default)]`; keep old baselines readable.
- [ ] Define:

      ```rust
      pub enum DiffKind { Unchanged, Added, Removed, Changed }

      pub struct DiffEntry {
          pub kind: DiffKind,
          pub scene_index: usize,
          pub scene_heading: String,
          pub base: Option<RevisionBlock>,
          pub current: Option<ScriptBlock>,
          pub current_block: Option<usize>,
      }

      pub struct DraftDiff {
          pub entries: Vec<DiffEntry>,
          pub added: usize,
          pub removed: usize,
          pub changed: usize,
          pub scenes_changed: Vec<usize>,
      }
      ```

- [x] Align scenes by stable block id, then `kit_uuid`, then heading text
      (with an identity-conflict guard), then shared body content and position.
      Reuse the bounded LCS and keep unchanged entries for context.
- [x] Compare any two `RevisionSet`s, and any set against current. Keep
      unchanged entries for context in side-by-side view.
- [x] Add unit tests for added/removed/changed/reordered/renamed scenes,
      duplicate headings, Unicode/Cyrillic, empty projects and determinism.
- [x] Add a 500-page performance test; target under 20 ms for a compare.

Acceptance:

- Comparing a baseline with itself returns zero added/removed/changed.
- A single edited block is reported as `Changed` in the right scene.
- A moved scene is not reported as a full rewrite.
- Results are deterministic across runs and platforms.

Status (2026-10-27): **done**. `DraftDiff`, `DiffKind` and `DiffEntry` are
public in `scriptcraft-core/src/revision.rs`; `RevisionHistory` exposes
`diff_against_current(index, current)` and `diff_between(base, target)`.
Removed scenes use target insertion indices, pre-heading blocks are grouped
with scene 0, and old baselines without `block_id` fall back to content
matching. 17 draft-diff regression tests plus the 500-page compare gate pass.

Estimate: 1 week.

### M2 — Compare workspace

Goal: a dedicated, read-only comparison view that a writer can actually use.

Tasks:

- [x] Add `scriptcraft-app/src/compare_view.rs`; keep it out of `app.rs`.
- [x] Base selector: any revision set. Target selector: any other revision set
      or the current draft.
- [x] Unified view and side-by-side view. Synchronised scrolling in
      side-by-side mode.
- [x] Change list with filters: all, added, removed, changed. Group by scene;
      show scene number, heading and counts.
- [x] Selecting a change reveals it in context; double-click, Enter or
      **Open in editor** jumps to the current block (removed blocks jump to
      the nearest surviving scene block).
- [x] Keyboard navigation: J/K or arrows for next/previous, Enter to open,
      V to toggle the view, Escape to close.
- [x] Read-only: never mutate the project or the revision history from the
      compare view. Toolbar editing, undo/redo and FastFormat are disabled
      while comparing.
- [x] Add kittest interaction tests and snapshots: open, filter, jump, toggle
      view, close; verify cursor/selection placement and read-only behaviour.

Acceptance:

- A writer can open Blue vs current, filter to changed blocks, jump through
  them, and return to the editor at the right place.
- No project mutation occurs while comparing.
- Long scripts scroll smoothly; only visible rows are laid out.

Status (2026-10-28): **done**. The compare workspace is a full read-only
view with base/target selectors, unified and side-by-side rows, a grouped
change list with filters and counts, and keyboard navigation. The main diff
is virtualised with `show_rows`; both side-by-side columns share one scroll
area, so they stay aligned. Opening a project or changing the revision
history closes the workspace, and edits invalidate an open comparison.
Three kittest tests cover open/filter/next/jump/close, read-only behaviour
and lifecycle; two snapshots cover unified and side-by-side layouts.

Estimate: 1.5–2 weeks.

### M3 — Restore as a copy

Goal: recover an earlier draft without ever overwriting the current one.

Tasks:

- [ ] Add `kitsp::restore_revision_as_copy(path, set, out_path)`.
- [ ] Whole-script restore only in v0.8. Scene-level restore is a later
      feature; do not pretend it exists.
- [ ] Save-as dialog with a suggested filename such as
      `<project>-<colour>-<date>.kitsp`; refuse to overwrite the current file.
- [ ] Preserve metadata and title page where the baseline has them; otherwise
      keep current metadata and warn that the baseline did not store it.
- [ ] Open the restored copy after saving; leave the current document dirty
      state untouched.
- [ ] Tests: original file unchanged, restored file opens, comparing restored
      baseline to itself is empty, metadata is preserved.

Acceptance:

- Restoring Blue creates a new `.kitsp`; the current draft is byte-identical
  afterwards.
- The restored copy opens with the correct script, page locks and revision
  history.
- The warning appears when a baseline lacks title-page/metadata information.

Estimate: 0.5 week.

### M4 — Omitted scenes

Goal: a scene can be omitted without losing its identity, number or revision
history.

Tasks:

- [ ] Spike the real representations: produce a final Draft `.fdx` and KIT
      `.kitsp` containing an omitted scene; record the exact XML/SQLite shape in
      `docs/format-spikes.md`. Do not guess.
- [ ] Add `omitted: bool` to scene metadata (M0). Prefer the sidecar if KIT has
      no native representation; document the limitation.
- [ ] Render an omitted scene as a retained scene heading plus an `OMITTED`
      line, with no body pages. Keep the scene number and revision colour.
- [ ] Exclude omitted body text from page counts and statistics, but keep the
      scene visible in the navigator and reports.
- [ ] FDX import/export mapping for the real representation found in the spike.
      KIT export must warn if omission cannot be represented.
- [ ] Tests: numbering, pagination, PDF parity, FDX round-trip, page-lock
      interaction, revision marks, reopening.

Acceptance:

- Omitting scene 12 leaves scene 12 numbered and visible, prints `OMITTED`, and
  does not consume body pages.
- A locked page before the omitted scene keeps its label; later pages keep
  their numbers.
- FDX round-trip preserves the omitted state where the format supports it; the
  conversion report names the loss otherwise.

Estimate: 1 week (after the spike).

### M5 — Dual dialogue

Goal: two consecutive dialogues can sit side by side in the editor and PDF
without breaking pagination or FDX interchange.

Tasks:

- [ ] Spike the FDX and KIT representations with real files; record findings in
      `docs/format-spikes.md`.
- [ ] Choose a model that does not corrupt ordinary KIT round-trips. Preferred
      order:
      1. a sidecar dual-group keyed by stable block IDs;
      2. an explicit block type if the format supports it natively.
- [ ] Extend `scriptcraft-layout` with a two-column placement path. Keep the
      existing single-column path untouched for normal blocks.
- [ ] Add the editor command (`Cmd/Ctrl+D`) and toolbar action; both blocks
      must be reversible with undo/redo.
- [ ] Handle `(CONT'D)`, parentheticals, scene characters and page breaks
      inside dual groups.
- [ ] FDX import/export and PDF rendering must use the same placement model as
      the editor.
- [ ] Tests: layout parity, PDF parity, FDX round-trip, undo/redo, 500-page
      performance, and an A95 regression.

Acceptance:

- Two selected dialogues render side by side in the editor and PDF.
- Page breaks and `(MORE)`/`(CONT'D)` behave correctly.
- FDX round-trip preserves the pairing.
- Undo restores the previous single-column state.

Risk: this is the highest-risk milestone because it touches pagination. If the
spike shows the layout change destabilises locked pages, ship v0.8 without dual
dialogue and move it to v0.8.1 rather than risk the revision core. Make that
decision at the M5 gate, not at release time.

Estimate: 2 weeks.

- [ ] Persist through the existing metadata path; do not rewrite untouched KIT

- [ ] PDF preview and export use the same fields; FDX title page round-trips.

### M7 — Revision summary

Goal: answer "what changed in this revision?" without opening a diff.

- [ ] Build `RevisionSummary` from `DraftDiff`: revision colour/name/date,

- [ ] On-screen summary table grouped by scene, with a totals row.
- [ ] CSV export with stable columns and UTF-8 (BOM optional for Excel).
- [ ] Printable summary view; PDF can follow in v0.8.1 if the layout work

Acceptance:

- Blue vs current produces a summary whose counts exactly match the compare

- [ ] Windows: choose a signing path (Azure Trusted Signing or an OV

- [ ] Derive `ROW_MM` from the TTF metrics (e.g. `ttf-parser`) and add a test

- [ ] Add a benchmark harness (`criterion`) for load, relayout, diff, compare

- [ ] Preserve unknown `scenario_data` rows on save; add a test.

Acceptance:

- A downloaded macOS build passes `codesign --verify` and `spctl --assess`.
- Windows/Linux CI launches the app and fails on a startup crash.
- Dock ▸ Quit shows the save prompt.

Estimate: 1–2 weeks, parallel with feature work.

## Architecture decisions

1. **`.kitsp` remains canonical.** ScriptCraft-only data lives in versioned
   `scenario_data` rows that KIT ignores. No new native format in v0.8.
2. **Stable IDs are persisted, not regenerated.** `ScriptBlock.id` and
   `SceneId` survive save/reopen. Re-anchor when an external KIT edit changes
   the block list; warn on ambiguity.
3. **Compare is block-level.** No character-level diff and no track-changes
   engine. The revision model is about production pages, not Word-style
   accept/reject.
4. **Restore is copy-only.** Never overwrite the current draft. Scene-level
   restore is explicitly deferred.
5. **Omitted and dual-dialogue state prefer sidecar metadata** unless the spike
   proves a native KIT/FDX representation can round-trip safely. The sidecar
   must be versioned and preserved by the normal save path.
6. **One layout engine.** Editor and PDF must share dual-dialogue and omitted
   scene placement. If they diverge, the release is not done.
7. **No plugin API, no collaboration, no AI in v0.8.** The interface surface is
   not stable enough to promise.
8. **The app crate gets smaller, not larger.** Every new view lands in its own
   module.

## Risks

| Risk | Mitigation |
|---|---|
| Dual dialogue destabilises pagination and page locks | Spike first; feature-gate; ship v0.8 without it if the core is at risk |
| FDX omitted/dual representation is unclear | Inspect real FDX files; document the exact shape; add round-trip tests |
| External KIT edits break IDs | Re-anchor by UUID/content/neighbours; warn, never silently drop |
| Sidecar rows are lost by a save path | Preserve unknown rows; A95 + explicit tests |
| Windows signing is slow/expensive | Decide by week 4; document SmartScreen if deferred; don't claim signed |
| Auto-update bricks installs | Checksum + signature; no silent install; manual download fallback |
| `app.rs` refactor causes regressions | Extract one module per commit; no snapshot changes; full suite |
| Scope creep from "professional" checklists | Enforce non-goals; validate with 5–10 writers before v0.9 |
